# i18n — content translation

Integrator-facing version: [../guide/translation.md](../guide/translation.md).
Original spec: [../guide/translation-ui-proposal.md](../guide/translation-ui-proposal.md).

## One layout, per-locale values

The structure of an area — sections, columns, block order, styling — is
language-agnostic and stays **shared**. Only fields a block type tagged
`cb_translatable` are swapped per locale. That is what makes a translated page
structurally unable to drift from its source.

Installing the bundle changes nothing about existing output: with no translation
rows and no locale resolved, the render pipeline returns the block's own data
untouched.

## Why a side table, not an envelope in Block.data

The alternative was a locale envelope inside `Block.data`, which rides along
every clone, export and import for free. It was rejected for one reason: **an
envelope is opaque.** "Which pages are missing German?" would mean deserializing
every block's JSON, so there could be no progress view and no filtering — and a
multilingual site is run from exactly that view.

The cost is the mirror image, and it is real: every flow that *duplicates* a
block has to be taught to duplicate its rows (`TranslationCloneObserver`, riding
the core's [clone observer seam](rendering.md#why-the-clone-notification-is-an-observer)),
every flow that *serializes* one has to be taught to carry them
([below](#translations-in-an-export)), and the render path needs a prefetch to
avoid an N+1.

The FK is `onDelete: CASCADE` rather than a lifecycle listener: a deleted block
has no translations by definition, and the database is the only place that can
guarantee that without every delete path opting in.

### The value shape

Values are a **flat map of path → value**, not a mirror of the block's data tree:

```json
{"title": "Bienvenue", "items[9f2c1a].label": "Livraison rapide"}
```

Flat means counting translated fields is `count()`, and a per-field merge is a
loop rather than a recursive diff.

### Draft and published mirror Block exactly

`draftValues === null` means *no pending translation edit*, and the effective
payload is draft-or-published in PREVIEW, published-only in PUBLIC — the same
rule `CoreBlockDataResolver` applies to `Block.data`, so a translation never lags
a mode behind its source.

Translations therefore go live through the same Publish button as the content
they translate, which is the point: **a French heading must not appear publicly
while the English heading it was written against is still an unpublished draft.**
See [publishing.md](publishing.md#the-invariant-the-shape-enforces).

The first write of a field copies the published payload into the draft, so a
partial edit does not silently unpublish every other field of the block.

### Translations in an export

`TranslationTransferExtension` is the clone observer's counterpart for a payload
that leaves the installation, riding the core's
[transfer seam](transfer.md#what-is-stored-beside-a-block). Without it an export
produces a page that comes back structurally identical and completely
untranslated — the failure is silent, which is what makes it expensive.

Three decisions inside it:

- **Draft-or-published, per row**, the same rule the renderer applies, so an
  export mirrors what the exporter saw rather than a state nobody is looking at.
- **Digests travel beside their values, never recomputed.** A digest asserts
  *this was translated from that source*, which only the side that translated it
  can know; re-hashing the incoming source on arrival would report every stale
  field as fresh. A fragment that carries no digests stays without them —
  absence is already read optimistically.
- **Every locale is imported, configured here or not.** A row for an unconfigured
  locale is inert (`RequestRenderLocaleResolver` resolves targets only), so
  keeping it costs nothing and dropping it would destroy content that an install
  one config line away can use.

Rows land in the **draft**, like every other write of this package: the area's
next Publish commits the imported page and its translations together.

## Paths and patterns

Two spellings, and the difference matters:

| | Looks like | Produced by |
|---|---|---|
| **pattern** | `items[].label` | the core's `TranslatableFieldsInterface` — a *shape* |
| **path** | `items[9f2c1a].label` | a stored translation — every `[]` filled with an entry's `_id` |

Keying by `_id` rather than by position is the whole reason [`_id` exists](clipboard.md#stable-entry-ids):
an editor who reorders, deletes or duplicates a card must not find the German
title of card 1 attached to card 3. Positions move; ids do not.

An entry carrying **no `_id` is skipped, not guessed at.** That happens for
content written before the ids shipped; `content-blocks:backfill-collection-ids`
is the fix, and skipping means such an entry reads as "not translatable yet"
rather than silently binding a translation to a position.

`FieldPath` is a grammar, not a service — every method is pure and static.

A few behaviours that look arbitrary and are load-bearing:

- **Expansion is driven by the data.** A collection with three entries yields
  three paths, an empty one yields none, and a key absent from `$data` yields
  nothing. Fields that do not exist are not untranslated work.
- **`has()` is not truthiness.** An empty string is a translation — "this heading
  is blank in German" — so merging on truthiness would lose deliberate blanks.
- **`write()` only writes into structure that already exists.** A missing key, or
  a collection with no entry of that id, leaves the data untouched. Creating the
  missing branch would let a stale translation resurrect a field the source has
  since dropped, or invent a card that no longer exists.
- **`segments()` returns `[]` for anything the grammar does not wholly consume**,
  which makes a malformed key from an untrusted payload a no-op everywhere rather
  than a partial match somewhere. The `(?=.)` after the separator is what rejects
  a trailing dot: without it `title.` would parse as `title`, quietly aliasing two
  spellings of one key.
- **`entryIndex()` is for labelling only.** "Card 2 · Title" reads better in a
  list than `items[9f2c1a].title`, and it is derived at display time precisely
  because it is the thing that moves when an editor reorders.

## Three states, not two

*Translated vs not* is easy to compute and useless to an editorial team. The
field that costs money is the one that **was** translated and whose source has
since been rewritten, because nothing about the page looks wrong: the German is
there, it is simply describing last month's offer.

| State | Meaning |
|---|---|
| `MISSING` | no stored value |
| `TRANSLATED` | stored, and the source still hashes to what it did |
| `OUTDATED` | stored, but the source changed afterwards |

An outdated translation is **still rendered** — a stale translation beats an
English paragraph on a German page — and flagged so an editor can decide.

### The digest is the whole mechanism

Hash the source when the translation is saved, re-hash it when the page is
inspected, and a mismatch means the source moved. No timestamps, no revision
numbers, no diffing — and crucially, nothing that a save of an *unrelated* field
can perturb.

Value and digest are written in a single call, because a digest that drifts from
its value is worse than no digest: it would report a fresh translation as stale,
or hide a genuinely outdated one. Digests are kept per state so a published
translation can still be reported stale after a publish cleared its draft.

**Byte-exact by design.** A whitespace-only edit to the source is a change: the
editor decides whether it matters, and a *mark as up to date* click costs one
second, whereas normalizing away a real edit costs a wrong page.

16 hex characters of SHA-256 — long enough that an accidental collision silently
hiding a stale translation is not a thing that happens, short enough that the
digest map stays smaller than the values it annotates. Values are JSON-encoded
rather than cast, so a host tagging something that is not a string gets a stable
representation instead of `"Array"`.

**A translation stored without a digest is not reported stale.** It predates the
mechanism or came from an import, and flooding the workbench with false alarms on
day one is worse than a missed flag — the pessimistic reading has to be earned by
an actual mismatch.

## The allow-list runs again at render

`TranslationWriter` already refuses to store a value for an untagged field, so
re-checking at render looks redundant. It is not: **tags are code and rows are
data, and code changes.** A field that was translatable last release and is not
any more has rows sitting in the table, and without the second check they would
keep overriding a field the block no longer considers translatable. The tags are
the current truth, so the tags win.

Fallback is **per field, not per block**. A field with no stored value keeps its
source text. Falling back for the whole block as soon as one field is
untranslated would make a half-translated page look broken rather than
incomplete, and would make incremental translation pointless since nothing shows
until everything is done.

The resolver runs at **priority 128** — below the core's seeding resolver (256),
above the default 0. Translation is closer to *what the payload is* than to a
transformation of it, so a host resolver substituting tokens or injecting
computed values at the default priority sees text already in the right language.

## One walk, one order

Progress, the workbench and the bulk translator all need the same walk, and two
of them producing different orders would show up as a workbench whose rows do not
line up with its own progress bar. So `AreaWalker` is the only walk.

It encodes two rules:

- **soft-deleted entities are skipped.** A block in the trash is not untranslated
  work; counting it would make a complete page report 94%.
- **ordering is by `previewPosition`**, not the collections' own
  `OrderBy(position)`. `position` is the *published* order, while the builder —
  and therefore anyone translating — sees the draft order. The sort has to be
  explicit because the Doctrine mapping cannot express it.

`BlockRef` carries 1-based positions computed at walk time rather than stored,
because "Section 2 · Column 1 · Block 3" is the only name for a row that does not
require understanding the block's contents, and it changes whenever anything is
reordered.

## Two readers of the form, one reader of the tag

`FieldMetadataReader` reads the *presentation* of a block's fields — label,
translation domain, which widget to render. It is deliberately **not** the
authority on which fields are translatable; that stays
[`TranslatableFieldsInterface`](forms.md#which-fields-are-translatable) in the
core, where the `cb_translatable` convention is frozen.

Two readers of the same tag would eventually disagree. Here there is one reader
of the tag and one reader of everything else, joined by path pattern, and
`FieldCatalogMatchesCoreTest` pins that the join covers every tagged field of
every kit block.

Reading the built form also means a field a host added through a
[form extension](forms.md#why-form-extensions-are-a-package-seam) arrives with its
label already correct, without the host registering anything here.

Three details:

- Symfony's humanize fallback is **reproduced** rather than reached for, because
  a `FormView` would mean instantiating data mappers for every block on the page.
- The rich-text widget is detected by **block prefix**, not class: the kit's
  rich-text field is a custom type wrapping a textarea, there are as many such
  types as editors a host might wire, and this package does not require the kit.
- Anything unlisted renders as a single-line text field — the safe default, since
  it renders every value and mangles none.

### Why that cache is per-request

`FieldMetadataReader` implements `ResetInterface`. It memoizes what a *form*
produced, and a form is allowed to vary with the ambient request: a host
extension can add a field for one role and not another, so the shape pinned by
the first `$data` seen would otherwise stay pinned for the life of the process.
Clearing it between requests is what makes a worker behave like PHP-FPM instead
of like whoever hit the page first. See [worker-mode.md](worker-mode.md).

The cache key ignores `$data` because data only affects conditionally-declared
fields, and a miss there costs a humanized label rather than a wrong one.

## The workbench is a page, not a panel

The unit of work is the **page**, not the block, so the workbench is a standalone
page this package renders in full — not a panel inside the builder.

It is rendered **server-side with its field list already in it**, rather than as
an empty shell filled over XHR. A translator's first action is to read and start
typing, and a spinner between the click and the first field is exactly the
latency the design exists to remove. The JSON endpoints next door remain the API.

`areaFields` returns the whole page in one request. Forty blocks is a few hundred
fields — small next to the block payloads the builder already moves — and having
it arrive at once is what lets an editor tab from field to field with no round
trip per row.

The route is `/area/{id}/fields/{locale}` rather than `/area/{id}/{locale}`
because the latter is ambiguous with `/area/{id}/locales` and would resolve only
by declaration order, which is a trap for whoever reorders the methods.

### Null clears, empty string stores

`{"values": {"<path>": "<text>|null"}}`. **`null` clears** a translation, so the
field falls back to the source; `""` stores a deliberate blank. The distinction
is load-bearing, not pedantry.

Anything that is neither a string nor null is refused before it reaches the
writer: the shape is the API's contract, and coercing an array or a number into
text would store nonsense under a valid path.

Writes authorize against the block's **own** area, not one named in the request,
so a forged block id fails the host's `canEdit()` rather than writing into a page
the editor has no rights to.

### The preview pane

The pane loads the **host's own** resolver URL with `?cb_preview=1&cb_chrome=0`
plus the locale. Reusing the host resolver rather than asking for a second,
locale-aware one is what keeps this working regardless of how a host spells a
locale in its routes; `PreviewLocaleListener` is the other half, turning the
parameter into a request locale **only in preview mode** — so it is never a way
to change the language of a public page.

`cb_chrome=0` is what makes the pane readable: preview mode otherwise injects the
builder's toolbars and click-to-edit, which are dead ends here because this page
has no builder sidebar to open. See [rendering.md](rendering.md#why-chrome-is-a-separate-flag-from-mode).

### Why no Stimulus controller

Every other controller in the suite is a Stimulus controller declared in
`assets/package.json` and enabled in each host's `controllers.json`. The
workbench deliberately is not, and the reason is what it *is*: a standalone page
the package renders in full, which never loads the host's JavaScript bundle — so
there is no Stimulus application for a controller to register with.

Serving a self-contained ES module instead means the workbench works identically
under AssetMapper and Webpack Encore, needs no entry in any host's
`controllers.json`, and needs no asset recompilation in any sandbox. For one page
with one behaviour, that beats the wiring.

Those routes are read-only static files, so they carry no CSRF and no access
check — there is nothing there that is not already public in the package's
source. The `.css` / `.js` extension is kept out of the route for the same reason
the kit does it: PHP's built-in dev server shortcuts anything that looks like a
static file and never reaches the front controller.

## Machine translation is a seam

The package ships `TranslationProviderInterface` and **no adapter for any
engine**. Where a page's text is sent is the host's decision, and it must not
arrive as a transitive dependency of a page builder.

Empty is therefore the normal state, not an error. With nothing wired, the
template renders **no ⚡ button and no "translate the page" button at all**,
rather than affordances that could only fail — a button that always errors
teaches editors to distrust the ones that work. Two things are filtered out for
that same reason: the `NullTranslationProvider` placeholder, and any provider
whose `supports()` says no to this source/target pair, since an engine covering
European languages has no business offering a button on the Japanese column.

Per-field, per-block and whole-page all land on `MachineTranslator`, which
batches each into a **single provider call**. So "translate the page" is one API
round trip rather than one per string, and the buttons cannot drift apart in
behaviour. Omitting `paths` translates every field that is missing or outdated;
passing one path is the per-field button — same endpoint, same code path.

The HTTP path is synchronous on purpose: one batched call for a page is seconds,
not minutes, and an editor who pressed the button wants the result, not a job id.
A host translating hundreds of pages drives `MachineTranslator` from a worker
instead, which is exactly what the console command does.

Everything a provider returns is written to the **draft**, through the same
writer the manual editor uses, and nothing bypasses the translatable-field
allow-list. A bulk machine pass is a first draft, not a release.

The bulk command iterates over **ids, re-fetched after every clear**, not
entities. A large run must not hold one enormous unit of work, but clearing
detaches the blocks — and a translation row created against a detached block is a
*new entity found through the relationship* error at the next flush.

`content-blocks:i18n:status` exists beyond the UI because it answers "are we
ready to launch the German site?" across every page at once, and it is
scriptable: `--incomplete` exits non-zero so a release pipeline can gate on it.

## Translated values hold asset references too

This package is exactly why the asset sweep needs
[a seam](assets.md#three-seams-and-why-each-is-its-own-interface) rather than a
hard-coded list of tables. A translated rich-text value is a separate row in a
separate table carrying its own `<img src="/uploads/…">`, so an editor who
uploads an illustration while writing the German version creates a file no
block's data mentions anywhere. Without `TranslationAssetReferenceProvider` the
sweep would delete it and empty the German page.

Both slots are read, for the same reason the core provider reads both: published
values are on the public site now, draft values are one Publish away.

## Config and mounting

`locales` accepts both a flat list of codes and a map with display labels,
because both spellings are natural and making every host write the verbose form
buys nothing.

Locales are stored **verbatim** as the host spells them — `fr`, `pt_BR`,
`zh-Hant`. The package does not normalise BCP 47.

The bundle prepends its own Twig namespace (the workbench is a page it renders in
full) and its Doctrine mapping (a host should not hand-write a
`doctrine.orm.mappings` entry for a table it never touches). Both are guarded on
the extension being present, so the bundle still boots in a non-Doctrine context
such as a unit-test kernel.

Routes live under `/_content-blocks` by default so a host firewall pattern
covering the builder covers these too — but the mount point belongs to the host:
`config/routes/bare.php` carries them prefix-free. **Route names are identical
either way**, and the workbench generates every URL its JS calls with `path()`,
so nothing hard-codes a path.
